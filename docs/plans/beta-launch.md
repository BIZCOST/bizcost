# Beta launch plan: BizCost online, closed, on the web

The plan behind docs/ROADMAP.md §Milestone 4 "Beta launch". Status: **APPROVED** on 2026-11-04 with Q1–Q6 = A (D-350). The owner decided its direction on 2026-10-31 (D-347, «1أ-2أ-3أ»): the web app goes online first as a closed beta for businesses the owner invites; the mobile app comes later; it runs after M4 Step 2 and before Step 3. It starts on the owner's «ابدأ» and the owner's answers to the questions below.

## Goal

About 5–15 real businesses the owner invites (the owner's joinery among them) use BizCost on the internet, on a computer or a phone's browser, with their real data kept safe, and tell the owner what they think, while M4 goes on being built.

- **What they get:** everything released today: Smart Setup, the Costing Core (materials, products, recipes, purchases, expenses, running costs, product costs), Sales & Profit (sales, imports, orders, customers, payments, real profit, quotations and invoices). Nothing still `planned` (Stock, Usage & Waste) shows to them until its release (D-125).
- **What it is not:** the mobile app (still deferred, D-347), store builds, subscriptions or payments, open sign-up, a marketing site.

## What is already built for this (M1, deferred until now)

- Hosting design: Supabase in Mumbai (`ap-south-1`) and Vercel with functions in `bom1` (ARCHITECTURE.md §Environments & deployment).
- `db-migrate.yml`: migrations and Auth settings reach a hosted project only through it, staging first, production with the owner's approval (D-100, D-106). Never `supabase config push` by hand: the file holds the local stack's values, and a push of them would open sign-up (D-361).
- Runbooks: migrations, the `bizcost_api` password, key rotation, restore, a blocked `supabase.co`, a person's request, the weekly release (ARCHITECTURE.md §Runbooks).
- Security: tenant isolation, permissions and hidden fields on the server, cross-tenant attack tests, CAPTCHA hooks (D-062), Sentry with cost values redacted.

### 2. Vercel environment variables

Settings → Environment Variables. **Production** applies to `app.bizcost.ae`, **Preview** to `staging.bizcost.ae`. Each variable has a **Type**: **Secret** on the ones marked so, **Config** on the rest (`DATABASE_CA_CERT` too, so it stays readable). A saved Secret cannot be read back or turned into Config, so its value goes in the password manager first. On each Preview value marked **Secret** choose **Preview → Git branch `main`**, not all branches: another branch's preview then has no secret, and stops at its first request (D-362). Any change needs a new deployment; `NEXT_PUBLIC_*` values are built into the browser code.

**To deploy staging:** Deployments → **Create Deployment** → branch `main` (if Vercel asks which branch the commit belongs to, choose `main`). A push to `main` does it too. **To deploy production:** **Redeploy** its latest deployment, or Create Deployment with `release`. Redeploy keeps the environment of the deployment you chose, so on a Production one it never updates staging. Until a deployment has its values every page shows an error (the import's own build passes without them): that is expected.

**The fork test, once, before you type any Secret below** (D-362 left it open, D-366). It proves a fork's own `main` gets none of Preview's values, whatever the author check does:

1. Add a harmless variable `FORK_CANARY` = `hello`, Type = Config, Preview → Git branch `main`.
2. Fork the repository into a free GitHub organization of yours. In the fork, on its branch `main`, make `buildCommand` in `apps/web/vercel.json` start with `echo "canary=[$FORK_CANARY]" && `, and open a pull request from that branch to `BIZCOST/bizcost`.
3. In Vercel, read that deployment's build log. If Vercel asks you to authorize it first, do it this once: no secret exists yet.
4. `canary=[hello]`: stop, type no Secret on Preview, and tell Claude. The way out is to sign your commits and turn on Require Verified Commits, which a forged commit cannot pass.
5. `canary=[]` means the guard holds only if the test could see the variable (a mistyped name reads the same). So change the variable's scope to all of Preview, redeploy that deployment, and read the log again. `canary=[hello]` proves it: the scope to `main` is what kept it out. If it stays empty, check the name; if the name is right, a fork gets no Preview values at all, which is safe too. Then delete the variable, close the pull request and delete the fork.
